AI/ML Security Assessment & Red-Team Methodology

Gavin Branaa · Independent Security Researcher · github.com/tritsystem · portfolio

A repeatable engagement process for finding, proving, and reporting real security issues in AI/ML systems — from the model to the infrastructure it runs on. The discipline below is the same one behind a published CVE, 35 merged fixes across 16 projects, and tooling that separates a scanner's noise from a verified finding.

Core principle. A tool signal is a lead, not a finding. Nothing reaches the client until it is reproduced on the real system, root-caused, and shown with a working proof of concept. Reporting a false positive costs more than reporting nothing — so the method is built to kill my own leads before they ever leave my desk.

The engagement — six phases

1 · Scope & threat model. What are we protecting, from whom, and what is the worst realistic outcome? Define the actors (anonymous → authenticated tenant → admin → insider), the assets (models, data, credentials, compute), and the blast radius. Read the target's own security policy first — if it disclaims a class, that class is hardening at most.
2 · Map the architecture & trust boundaries. Draw the data and control flow end to end: user → app → model → tools → data stores → infra. Every arrow that crosses a trust boundary is an attack surface. A diagram with the boundaries marked is the first deliverable — it makes the rest of the engagement legible.
3 · Enumerate attack surface, layer by layer.
LayerWhat goes wrong
Modelprompt injection (direct & indirect), jailbreaks, system-prompt / training-data extraction, unsafe output handling
Agent / toolstool abuse; the lethal trifecta — private-data access + untrusted-content ingestion + an exfiltration path in one agent
Applicationbroken access control / IDOR, cross-tenant isolation gaps, missing authorization on a sibling endpoint
Serving / infraunauthenticated code-exec endpoints (job-submit = RCE), SSRF to cloud metadata, unsafe deserialization
Supply chainmalicious models, pickle/torch.load RCE, checkpoint metadata driving an out-of-bounds kernel access
4 · Rank the targets. Score each candidate by exposure × ease × attacker-gain × blast-radius. Spend the budget where the payoff is highest, and write the ranking down so the client sees the reasoning, not just the results.
5 · Find → reproduce → verify (the evidence ladder). Every candidate is graded and never rounded up:
  • T0 static/tool hit · T1 read by hand · T2 run in a harness — all still just leads.
  • T3 reproduced through the system's real entry point — the minimum bar to call something a finding.
  • T4 T3 + a verified fix (red→green) · T5 + variant analysis across siblings.
Before anything is called real: scope-check the policy, trace to the actual enforcement layer (the guard often lives in a wrapper or middleware, not the handler), grep the project's own tests, and dedup against prior reports.
6 · Report — proof, impact, remediation. Each finding states the exact file/line root cause, a reproducing PoC, the honest impact (what an attacker actually gains, and the preconditions), and a fix that closes the class, not just the instance. Negatives are reported as rigorously as positives. Severity is never inflated.

Why this method is trustworthy

  • It has produced real, independently-confirmed results — a CVE, merged fixes in C, Go, and Python, and cross-tenant authorization fixes adopted upstream.
  • It is tooling-backed: a 40+-detector scanner with a learned gate that distinguishes a signal from a validated finding, plus metamorphic and sanitizer-driven verification — so breadth is fast and the bar stays high.
  • It is honest by construction: in a climate where AI-generated security reports are flooding maintainers, the value is not volume — it is a report a defender can act on without re-doing the work.

Engagement artifacts: a trust-boundary diagram, a ranked attack-surface map, a findings report (proof + remediation per issue), and a remediation-verification pass on request.
